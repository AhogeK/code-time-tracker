# Domain Knowledge Map — code-time-tracker

本仓库的领域知识库（R29 治理：该规则承载约束，本文件承载操作规程）。

## 两层分工

| 层 | 位置 | 回答 | 性质 |
|---|---|---|---|
| 时间线层 | `memory-bank/*.md` | "最近发生了什么" | 按时序演进，会被时间取代 |
| **领域层（本目录）** | `memory-bank/domains/<domain>/` | "这里什么是真的、该怎么做" | 耐久、经判断、永不是 changelog |

横切规范（命名、线程模型、错误处理、测试风格）留在 `systemPatterns.md`；领域文件只装**领域专属判断**，不得重复——重复即需合并。

**为什么结构优先于检索**：固定文件集是**覆盖约束**——它声明「在本领域行动前至少必须理解什么」。检索只能告诉你"什么看起来相关"，不能告诉你"你正缺哪条决定性约束"。先看结构，检索用于补结构未覆盖的部分。

## 如何读一个领域（渐进式披露）

不要一次读完整个领域树。每个文件回答一个问题，下一个文件由上一个答案决定：

| 步 | 读 | 回答 |
|---|---|---|
| 1 | `meta.md` | 这事归这个领域吗？在这里它叫什么？ |
| 2 | `scenarios.md` → `principles.md` | 适用哪条判断；两个选项冲突时谁裁决 |
| 3 | `practices.md` | 具体怎么做——参数、代码形态、坑 |
| 4 | `references.md` | 事实查表：端点、字段、常量、路径 |
| 5 | 源代码 / 配置 | 这些事实现在还成立吗（R29 回源） |

第 2–4 步不是固定顺序：契约问题可从 `references.md` 起；"为什么是这样"从 `practices.md` 起。

## 每领域文件集（R29——建立即填实，禁止占位）

| 文件 | 装什么 | 什么时候读 |
|---|---|---|
| `meta.md` | 边界、代码路径、阅读起点、术语、核对基线 | 还不确定领域是否适用 |
| `principles.md` | 不变量与第一性原理——冲突裁决依据 | 两个选项冲突需要决定规则 |
| `scenarios.md` | 触发 → 判断 → 动作 | 出现了熟悉的场景 |
| `practices.md` | 具体做法、参数、代码形态、坑 | 即将动手写代码 |
| `references.md` | 契约、端点、错误码、常量、路径 | 需要事实而非判断 |

**填不实的文件 = 领域还不该存在**——宁可不建，不要建桩。

## 维护

**增量（变更触发）**：契约或结构变化（同步 DTO、端点、SQLite schema、统计口径、图表层级）时，**同一轮**更新对应领域文件。自动化只负责发现变化、生成候选、阻止遗漏；高风险知识（同步协议、数据模型、统计口径）的语义确认归人。

**校准（复盘触发）**：大改造、事故复盘或 `../ctt-server` 版本变化后，对照代码重读领域文件查漂移。漂移靠主动看发现，不是等谁撞上过时指引。

**漂移处置**：领域文件与代码不一致时，先判定哪边是事实源，再编辑任何一边：

| 情形 | 动作 |
|---|---|
| 代码是当前行为，领域文件过时 | 修领域文件 |
| 领域文件记录的是意图规则，代码违反 | 那是缺陷——报告它，**不得**"修知识去迎合代码" |
| 双方都非权威（意图不明） | 标记 **待确认** + 写明什么能定论，不得静默二选一 |

**核对基线**：每个 `meta.md` 声明该领域上次对照来源核对的日期与版本，读者据此判断信任度。

**索引完整性**：本文件是地图，地图与地形不符比没有地图更糟。增删改领域后，同一轮更新上表。

## 已定取舍——不再重议

| 问题 | 决定 | 理由 |
|---|---|---|
| 与代码同仓库还是独立仓库？ | **同仓库**（`memory-bank/` 随 git 提交） | 知识须与所描述的变更同 commit 演进（R5/R7）；agent 在仓库内直接可读，无需额外同步步骤 |
| Markdown 还是 YAML？ | **Markdown** | 人与 agent 共读；表格已承载结构；当前规模（2 领域）下 YAML 的密度收益不抵可读性损失 |
| 每条事实存这里还是链接？ | **链接** | 重复正是漂移之源；每条事实只有一个家 |
| 结构优先还是检索优先？ | **结构优先** | 检索找到"看起来相关"；它无法告诉你缺了哪条决定性约束 |
